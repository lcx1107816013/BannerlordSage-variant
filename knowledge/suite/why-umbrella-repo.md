# 为什么是「伞仓」而不是「四合一真合并」

> 记录这个仓库**为什么长这样**。结论：**刻意不 vendor 三个上游**。

---

## 1. 起点：用户想"一个仓库"

原话是："把这四个 mcp 放到一个仓库不行嘛……建立一个四合一的联合仓库"。

需求本身完全合理：**一个地方能拿到全部**、不用记四个地址。

---

## 2. 但"四个 MCP"其实是三种东西

| # | 名字 | 性质 | 有上游吗 |
|---|---|---|---|
| 1 | `blbridge` | ★ **纯自研** | ❌ |
| 2 | `bannerlordsage` | 上游**变种** | ✅ `hby7921/BannerlordSage` |
| 3 | `bannerlordhelper` | 上游**变种** | ✅ `Gengark/Bannerlord-Helper` |
| 4 | `localization-audit` | ★ **纯自研** | ❌ |
| + | `bl_chain`（本桥） | ★ **纯自研** | ❌ |

⇒ **风险全部集中在 2 和 3。** 另三个本来就没上游，怎么放都行。

---

## 3. 真合并会永久丢掉什么

两个变种仓库各自带着**完整的 git 历史与上游 remote**：

| 仓库 | upstream remote | 提交数 |
|---|---|---|
| `bannerlordsage` | `hby7921/BannerlordSage` | 18 |
| `bannerlordhelper` | `Gengark/Bannerlord-Helper` | 40 |

它们的历史里存着"**上游原始提交 + 我们的改动**"的对应关系。

**一旦复制进新仓库并删掉老仓库**：
- 上游发新版时**无法再 `git merge` / `rebase`**，只能人工对着 diff 抄；
- `git log` 再也分不清"哪行是上游的、哪行是我们改的"；
- 而"**适配上游未来的更新**"是用户**早前明确要过的能力**。

⇒ **这是不可逆的**，而且代价会**随时间增长**（上游越发版，人工抄越贵）。

---

## 4. 所以选了伞仓

**本仓库 = 只放我们自己的东西**：

```
bl_chain.py            链桥本体
localization-audit/    第 4 个 MCP
tests/ probe/ tools/   验证与工具
docs/                  说明
```

**三个业务 MCP 各自保留自己的仓库**，通过 `DSH_CHAIN_*` 环境变量指过去。

### 它满足了原始需求吗？——满足了

| 需求 | 伞仓怎么满足 |
|---|---|
| "一个地方拿到全部" | ★ **README 顶部就列全四个仓库的地址 + 一条 `git clone` 命令**；全部路径都能用环境变量配 |
| "不用记四个地址" | README 一处列全；★ **`bootstrap.ps1 -Check` 会逐个点名缺哪个、并直接打印该执行的 `git clone`** |
| "一个入口" | ★ **`meta` 模式就是那个入口** —— 5 个元工具，**113 个能力**全在里面 |

### 代价

- ⚠️ 需要使用者 clone 多个仓库（**这是唯一代价**，且可用脚本自动化）。
- 若你确实**永远不需要上游同步**了，可以随时把它升级成"真合并" ——
  **伞仓是那条路的子集，不是反方向**。

---

## 5. 顺带记两个当时查出来的事实

### 5.1 有个"老仓库"确实可以删，但**不是**你以为的那三个

用户说"把老仓库删除掉"。先分清三个 remote：

| remote | 能删吗 |
|---|---|
| `lcx1107816013/Bannerlord-blbridge`（**文本通道**） | ✅ 可删 —— 与本项目主仓库**无共同祖先**，是**另一条通道**（36 vs 134 提交） |
| `hby7921/BannerlordSage` | ❌ **是上游作者的仓库**，你既没权限、也**绝不能删** |
| `Gengark/Bannerlord-Helper` | ❌ 同上 |

★ **"删老仓库"只对那个远端文本通道成立。**

### 5.2 路径硬化问题（已在本仓库修掉）

`bl_chain.py` 原来写死了本机路径（Python 解释器、用户目录下的 clone、Steam 游戏根）
⇒ **别人 clone 后一个上游都起不来**。

本仓库已把它们全部改成 **环境变量 + 兜底默认**
（当初的迁移脚本是 `tools/make_paths_portable.py`，**已完成使命、已删除** ——
一次性改动，留着只会让人以为还要再跑一次）。

★★ **2026-10-13 二次改进**（安全审计 L2）：原来的"兜底默认"是**写死一条本机路径**，
有两个问题：
1. 写死本机用户名 ⇒ 带进公开仓库；
2. ★ 写死的那条 BlBridge 路径**后来失效了**（目录还在、`tools\bl_mcp.py` 不在
   ⇒ 卸载残留的空壳）—— 而"目录存在"让这件事看起来像"环境变量没设"，
   本机因此长期 `blbridge: connected=false`，排查方向被带偏。

⇒ 现在改成**动态探测**（`tools/_paths.py`，单一真相源）：

| 机制 | 说明 |
|---|---|
| 环境变量优先 | `DSH_CHAIN_*` / `BANNERLORD_DIR`，与 `bl_chain.py` 同口径 |
| **marker 判据** | 用"目录里有没有那个**入口文件**"判断可用性，**不是**"目录存在" —— 后者被残留空目录骗过 |
| 运行时算用户名 | `os.path.expanduser("~")` / `%LOCALAPPDATA%`，源码里不出现本机痕迹 |

其中 `PY312` 的兜底一直是 `sys.executable` —— 谁跑本桥就用谁去起子进程。

★ 改动时踩过两个坑（都在脚本注释里记了）：
1. 替换顺序错了 ⇒ 把**刚插入的默认值**也替换成自己，得到 `X = _ENV(...) or X`（NameError）；
2. `r"..." + os.path` 拼接导致 `ros.path`（`r` 与 `os` 相邻）。

### 5.3 测试布局变化（已修）

上游布局是"所有脚本与 `bl_chain.py` 同目录"，其中每个脚本都 `import bl_chain`。
搬进 `tests/` 后**13/18 项立刻失败**（全是 `ModuleNotFoundError`）。
修法：`ROOT = os.path.dirname(HERE)` + 加进 `sys.path`；
审计自测另指到 `localization-audit/tools/`。
⇒ 改完 **18/18 通过**。
